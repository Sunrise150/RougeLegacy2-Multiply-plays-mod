## v3.0.24（协议 3012→3013）：失焦挂起 / 观战卡 / 门触发器回归
用户真机反馈三条：①门触发器又失效；②观战视角特别卡；③鼠标不在主机窗口上时客机画面极差，点回主机才好转；跨区域尚未验证。

**根因一（症状③ + 症状①的一半）：Unity "Run In Background" 默认关闭。**
反编译证据：游戏自己只有 `GameManager.OnApplicationFocus(false) -> WindowManager.PauseWhenPossible(true)`（GameManager.cs:78），从无 `Application.runInBackground` 赋值 —— 说明依赖 Player Settings 默认值（独立程序默认关）。关闭时窗口失焦 Unity 会【挂起整个主循环】：Update 不跑、onBeforeRender 不触发、不出帧。而我们整套联机逻辑恰好只挂在这两个回调上（`NetworkManager.Update -> PumpNetwork` 收发；`onBeforeRender -> Bootstrap.Tick` 兜底收发），门触发器自愈也挂在 `DownedManager.Update -> RoomFix.Tick -> DoorLinkFix.Tick` 上。所以失焦的那一方彻底停摆 —— 对端画面冻住、门不再自愈；鼠标点回窗口 → 恢复焦点 → 主循环复活 → 立刻好转，症状完全对上。
修法：新增 `BackgroundRun.cs`（已入 csproj）—— ①`Application.runInBackground = true`；②Harmony prefix 拦 `GameManager.OnApplicationFocus`，仅在"联机中 + 失焦"时返回 false 跳过原生暂停（ESC 暂停/手柄断开走别的入口不受影响，单机不受影响）。在 `Plugin.Awake` 里于 `PauseCompat.Apply` 之后立即注册。

**根因二（症状②观战卡）：分身插值三处缺陷。**
`RemotePlayerInterpolator.Update`（PlayerSync.cs）原来：①用受缩放的 `Time.deltaTime`（timeScale=0 时为 0 —— Boss 死亡定格 Cutscene 类型 PauseCompat 明确不拦、RLTimeScale 9 类型取最小值，残留一项 0 就永久 0）→ 分身原地冻住，观战镜头跟着分身走 → 整个观战画面卡死；②`Vector3.Lerp(pos, target, dt*18)` 的 t 未 Clamp01，低帧率下 dt*18>1 会过冲来回抖；③包里本来就带 vx/vy（`PlayerStateData.VelocityX/Y` = 角色 Velocity）但接收端完全没用 → 20Hz 位置包之间分身"站住等下一包"的台阶感。
修法：全改 `Time.unscaledDeltaTime`；`Mathf.Clamp01`；速度外推（`MaxExtrapolate=0.12s`，单次位移限幅 `MaxLead=2.5m` 防被击飞时冲过头）；`HandleRemoteTransform` 把 vx/vy 传进 `SetTarget`（新增 Vector2 重载，与原 bool freeze 重载不冲突）。

**根因三（症状①另一半）：门自愈的"进房多久"判定会被 timeScale 冻结。**
`RoomFix` 四处用 `Time.time - pc.TimeEnteredRoom`（受缩放时钟）。timeScale 卡 0 时 Time.time 停住 → 差值恒为 0 → `enteredFor > 1f` 永不成立 → `ActivateDoorTriggers` / `PokeStubbedDoorTriggers` / `MarkEntered` 全被跳过 → 门触发器彻底失效。
修法：新增 `EnteredForSeconds(pc)` —— scaled 与自记的 unscaled（`_roomEnteredAtUnscaled`，换房时记）取 max；两者皆不可信才回退 99f。scaled 优先（v3.0.20 已验证），unscaled 保证 timeScale=0 时门自愈仍能跑。
**注意纠错**：曾误以为"换场景 Unity 会把 Time.time 归零" —— 查证 decomp 全库无 `Time.time =` 赋值，Time.time 跨场景累加不变；真正的冻结源是 timeScale=0。已改正注释与实现。

**跨区域补全（症状④，用户尚未验证）**：`BiomeRoomBuilder.EnsureBiome` 原先只接在观战路径（`EnsureSpectateRoom`）。活着的跟随端在权威跨区时，biome 过滤会把本地旧区房间全排掉 → `ResolveTargetRoom` 必落空 → 只能重试到超时。新增 `RoomTravelSync.TryBuildRemoteBiome()`，在跟随重试到第 3 次时触发（留时间让"跟随端自己过门"先完成，避免与原生 BiomeTransitionController 并发建同一块 biome；转场中用 `SceneChangeSync.IsTransitioning` 挡）。

**新增诊断**：`DoorLinkFix.WarnIfDeadAtDoor` —— 玩家站在门口 3.5m 内而该门出口触发器仍未武装时立刻打警告（房间名/门号/距离/触发器状态/对面房间），这是"门触发器失效"的现场铁证，不再要等 5 秒一次的体检。

关键日志：`[BG] 窗口失去焦点：联机中继续保持运行`、`[DOOR] 玩家就在门口但触发器没武装`、`[DOOR] 体检`、`[ROOMSYNC] 跟随端跨区域：已触发本地补建区域`、`[INTERP]`。

## v3.0.25（协议 3013→3014）：跟随传送的落点/场景判定 + 开局交钱与"世界锁"同步
用户真机反馈六条：①门触发器又失效；②进城堡要"把钱全部交出"，但扣除的只是触发交钱那个人；③"世界锁"动画两端不统一；④客机进漂流屋，主机被直接传送到挑战里；⑤加长房间传送依旧错；⑥（用户认为最重要）开局不从默认出生点出生，而是出生在"离下一个房间最近的位置"。

**★ 核心发现：`PlayerExit(null)` 是游戏自己的"场景级/传送级进入"信号，绝不是过门。**
反编译全库只有五处这样调 `BaseRoom.PlayerExit(null)`：
1. `OnPlayManager.CreateInstanceOfBaseRoom`（OnPlayManager.cs:430）—— 开局进城堡的第一间房
2. `Tunnel.EnterTunnel`（Tunnel.cs:202）—— 隧道/分支，随后 `Destination.PlacePlayerHere()`
3. `ChallengeTunnelController.EnterTunnel`（ChallengeTunnelController.cs:120）—— 漂流屋的挑战
4. `ChallengeTunnelController.ReturnToDriftHouse` —— 从挑战回漂流屋
5. `MapController`（MapController.cs:1556）—— 地图传送
正常过门走 `OnPlayerExitViaDoor` → `PlayerExit(eventArgs.Door)`，door 一定非空。
而开局真正的落点是 `PlayerController.EnterRoom(room2, null, room2.PlayerSpawn.transform.localPosition)`（PlayerController.cs:1852）——**房间默认出生点**。
⇒ 旧版把"无门进入"也当成过门去广播，对端按"门内侧"落人 → ①客机开局被放到离下一间房最近的门边（症状⑥）；②队友进挑战时主机被一起拖进挑战（症状④）；③地图传送也互拖。
**修法**：`RoomTravelSync.PlayerExitPrefix` 里 `door == null` 时**不触发房间跟随**（并清掉残留的 `_exitArmed`）。开局由 `SceneChangeSync` 的场景同步负责（两端一起切 World 场景，各自由原生 OnPlayManager 落在默认出生点）。这是症状④⑥的共同根因。

**其余跟随判定加固**：
- `ResolveTargetRoom`：锚点命中后**必须再验证对端确实站在这间房里**（`RoomContainsPoint`，放宽 3m；Bounds 不可信时放行）。否则锚点会命中同坐标的邻居（漂流屋 vs 挑战房）。
- 落点链重构：先算落点再统一执行"退旧房/开新房/落人"（旧版三段重复代码易走样）；新增 `TryGetSpawnLocal`（`Room.PlayerSpawn`）作为兜底，并打印实际落点方式。
- `GetAllRooms` 排除"被合并掉的成员房"（`Room.GridPointManager.MergeWithGridPointManagers` 非空）——原生 `CopyRoom` 销毁成员房的 Room 组件是延迟到帧末的，那一小段窗口里成员房会被扫进房间表，坐标与合并房重叠 → 症状⑤。

**新增 `RunStartSync.cs`（已入 csproj）+ `MsgType.RunStart = 61`（协议 3014）**：同步开局流程。
- 原生：HubTown 里和 Charon 说话 → `PlayerSaveData.GiveMoneyToCharon(caller)`（**全部金币交出**，GoldCollected 归零，派发 GoldChanged/GoldSavedChanged）；和 Architect 说话 → `ArchitectShop.SetLockState(CastleLockState)`（**这就是"世界锁"**：Animator Fire/Retract + mechanismLock/UnlockAudioEvent + 写 `PlayerSaveData.CastleLockState`）；`LevelManager_RL` 据此加载 World 开新局。
- 问题：这两步都是本地 UI 交互，联机时主机点了、客机只被 SceneChangeSync 拉去换场景 → 客机金币没归零、锁状态不一致、动画音效对不上（症状②③）。
- 修法：patch `GiveMoneyToCharon` postfix 广播"交了钱"；**锁状态用轮询检测**（`SetLockState` 是迭代器方法，Harmony 打迭代器 postfix 时序不可靠）→ 新增 `RunStartSync.Tick()`（挂 NetworkManager.LateUpdate）。收到端调用**游戏自己的**同一套逻辑：`psd.GiveMoneyToCharon(null)` + 通过反射跑 `ArchitectShop.SetLockState` 协程（找不到 ArchitectShop 就只同步状态）。`_applyingRemote` 防回声。

**仍需用户确认**：门触发器（症状①）本轮没定位到根因 —— v3.0.24 已加现场诊断 `[DOOR] 玩家就在门口但触发器没武装`（房间/门号/距离/触发器状态/对面房间），需用户提供该行日志，**并确认这次测的是哪个版本**（症状是在 v3.0.24 之前还是之后）。跨区域（症状之外）仍未验证。
关键日志：`[ROOMSYNC] 场景级/传送级进入（无门），不触发房间跟随`、`[ROOMSYNC] 跟随落位方式：...`、`[RUNSTART] 广播/套用对端开局状态`、`[DOOR] 玩家就在门口但触发器没武装`。

### 编译踩坑（v3.0.25）
`RoomContainsPoint` 报 CS0023「运算符"."无法应用于"void"类型的操作数」——**Unity 的 `Bounds.Expand(Vector3)` 返回 void**，它是【原地】放大而不是返回新 Bounds。必须先 `Bounds expanded = b; expanded.Expand(...);` 再 `expanded.Contains(p)`，不能链式写 `b.Expand(...).Contains(...)`。项目里已有的 `FindRoomAt`（RoomTravelSync.cs:1117）用的就是"先复制再 Expand"的正确写法，可作对照。

**① 加长房间"位置不一致"的根因（已修）**：`RoomTravelSync.TryWorldLandingLocal` 原来**无条件**把落点朝房间中心内缩 1.6m + 向下贴地 1.1m。对普通房无所谓，但对**合并房**（加长房，Bounds 巨大、中心在整段中间）会把客机往里推 1.6m 且高度与主机不同 → 两端坐标错开。原生 `BaseRoom.PlacePlayerInRoom(door)` 把人放在门内侧（已经在房里），本来就该原样落地。
